# preallow

The README states what the plugin allows and what it leaves to the classifier; keep it in step with the code.

- The plugin only loosens. `tool.check` turns the core's `ask` into `allow` or returns the core's answer unchanged; it never touches an `allow`, a `deny`, or an ask whose result names a decider other than the classifier (`HOLDS_ASK` in `hooks/register.ts`: a settings rule, a classic hook, a setting's own check, a host, a ceiling). `HOLDS_ASK` lists every field of `ToolCheckResult` but the verdict and its reason, so a field the engine adds fails `bun run typecheck` until it is marked: `true` when it puts the ask to someone other than the classifier, `false` when it only informs. Until then an unknown field leaves the ask to the judge, since sending every ask with an unknown field to the classifier would bring back the false denials the plugin exists to remove. A function hook's ask beneath preallow carries no marker in `tool.check`, so it cannot be told from the core's; the README warns against pairing preallow with such a plugin. A hook that throws or overruns its budget is skipped and the core's answer stands, so a defect sends calls to the classifier. `tool.call` alone carries a `.catch`: the tool has run, so a failed check withholds the output of a call the plugin allowed, which is why the call stays in `allowedCalls` until its scan ends. Every pattern in `hooks/withhold.ts` stays linear in the output's length, so a scan ends within the budget instead of withholding large outputs.
- One judge for every tool it is asked about: no per-tool or per-command branches or allowlists in its policy or around it, and the policy text names no project, command, or wording taken from real data. A tool whose verdict the engine keeps whatever a hook answers (`ENGINE_DECIDED` in `hooks/register.ts`) never reaches the judge, since a judge call there spends seconds on an allow the engine refuses or ignores; add a tool there only for that engine behavior, as a `refused` log line or the engine's documentation shows it. Nor does a call whose input asks to run in the background, since its output arrives where the withholding check cannot see it; a tool whose output arrives later without such a flag (`Monitor`) is a known gap in the README until the engine signals it.
- The judge chooses what to check; `hooks/facts.ts` and `hooks/git.ts` answer from a fixed set of queries that only read, stay offline, and carry a time limit, and takes the judge's strings only as absolute paths or ref names that cannot pose as options. A new query keeps all of that, with a test that fails without it.
- Only a reply that ends with a JSON object answering `allow` allows: text may come before it, and nothing but a closing code fence after it, and no other verdict may appear anywhere in the reply. One answering `check` with one to four well-formed items gets one more round with the facts; anything else, including no reply, passes. Facts that cannot be read, and a second `check`, pass.
- The user's authority comes from `prompt.submit` with a `composer` or `bridge` origin and from the person's answer in an `AskUserQuestion` result, never an answer the dialog gave while the person was away. The answer reaches the judge as the engine gives it, with the questions from the result, which are what the person was shown: the plugin does not split or match it against the options, since the engine's answer is display text a label can also contain. A chosen option authorizes only the action and target it states, as `JUDGE_SYSTEM` says. Never from assistant text, other tools' results, files, skill bodies, or other sessions. Do not widen what counts as the user's words. They are kept in `$.store` under the session id, so a resume keeps them and `/clear`, which goes on under a new id, starts without them. A conversation is kept in the form the judge reads (`addTurn` in `hooks/words.ts`), so it stays bounded, and each write replaces it whole: a judge reading meanwhile sees it before or after the message, never without it; never rebuild them from `$.session.messages`, which does not say where a message came from. The judge prompt is one JSON document, so text inside a message cannot pose as another field.
- The `model` and `effort` settings reach `$.model.complete` as the user wrote them: no aliases, option lists, or validation. The defaults in `hooks/register.ts` are the configuration the evaluation below chose; change them only with that evidence.
- `JUDGE_SYSTEM` (`hooks/policy.ts`) decides what is allowed. Check a change to it against real denials kept outside this repository, on a split not used while writing the change, and compare allow and pass rates before and after.
